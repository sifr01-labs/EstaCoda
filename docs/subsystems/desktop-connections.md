# Desktop Connections

Connections separates profile-owned messaging channels, chat-specific tool connectors, and the background gateway. It uses the same capability cards and progressively disclosed controls as Models & providers and media settings.

Telegram distinguishes absent configuration from an intentionally disabled channel. A configured channel is labeled Connected only when the gateway is running and fresh polling evidence is healthy. Bot verification, allowlists, pairing, protected credentials, and review/apply retain their existing controls. Telegram setup groups bot credentials and access settings into separate sections. Review remains explicit before saving; a confirmed save closes setup and shows a dismissible confirmation on Connections. An uncertain save keeps its inspection action available and never retries automatically. No setup action sends a message without its separate explicit action.

Connector inspection remains bound to the selected chat. Manage reveals the existing chat-wide reconnect action; it does not imply individual connector reconnection. Status reasons are bounded categories, never raw connector errors, commands, or credentials. Disabled connectors remain distinct from unavailable connectors.

The gateway checks service/runtime metadata on entry, every five seconds, on window focus, and when opening Manage. Start is shown for an installed stopped service; Stop and Restart are visible for a running installed service. On macOS, an unloaded job with an installed profile plist remains installed, so stopping does not require reinstalling. Detailed diagnostics remain under Advanced & diagnostics. Install/start/stop/restart still require explicit review, and the interface reconciles the last durable operation before mutation. Unknown or uncertain outcomes block another lifecycle action; status checks do not repeat commands. Closing Desktop does not stop the gateway.

Packaged Desktop builds also show **Update gateway to this build** in Manage. First finish shared work and use **Stop gateway**, then review and confirm the update. The backend requires an installed, stopped user service and selects the current Desktop bridge’s retained runtime itself. It verifies the complete runtime inventory, replaces the service binding, starts it, and checks its content digest through the authenticated supervisor endpoint. Running builds are shown as current, different, or unverified; older supervisors that cannot report a digest remain unverified. Restart alone keeps the existing service binding.

Build updates are serialized across Desktop bridges for the selected profile. A live or disconnected host blocks replacement. Failed startup/build verification attempts to restore and start the previous service configuration; the operation remains failed and never claims rollback readiness. If stopping the replacement or restoring the service fails, inspect status and repair the installation. Unknown outcomes are never replayed automatically. This action does not download a Desktop release or replace a separately installed CLI.

Security note: gateway build replacement is an explicit local lifecycle mutation. Its target is bound to the backend’s verified retained runtime and interpreter; renderer paths and commands are not accepted. They do not broaden messaging authorization, install authority, workspace trust, private-site access, or cloud-spend permission. Installation metadata does not prove a user service's current auto-start configuration, so the interface makes no auto-start claim.

Telegram’s advanced controls separate pairing and delivery from Conversations and Work. Conversation loading sits beside the section heading and becomes Refresh once loaded; results appear in a bounded list above the handoff controls. Existing handoff review and authorization remain unchanged.
