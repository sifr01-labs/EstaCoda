# Desktop targets and managed worktrees

Desktop PR9 adds target inspection and reviewed Git worktree creation to the existing Work interface. Core remains the sole owner of target records, trust checks, generations and cleanup. Target IDs and displayed paths are references, not execution authority.

## Select and create

In New chat, use **Manage workspaces** to inspect existing targets. Select a ready target and choose **Use for new Work**. Switching a draft’s target clears its attachment references; the prompt stays in the draft. Existing Sessions and Tasks retain their original target and working directory. Their **Inspect target** control does not rebind them.

Source discovery uses the current profile’s core target records. To make a source available, select an existing local repository through the CLI or setup and grant workspace trust there. A workspace alias alone is not a target: the ordinary trusted launch acquires the target. The repository needs a committed HEAD. Desktop does not yet offer a native folder-registration workflow.

Select a ready local repository and choose **Create worktree…**. Review the profile, source path, new directory, generated `estacoda/<operation UUID>` branch and starting commit. Confirm trust for the new directory, then create it. Review tokens expire after five minutes and are invalidated on bridge/profile changes. Source trust is checked again at creation; changing HEAD after review requires a new review. Uncommitted source changes are not copied into the worktree.

Trust remains global directory action trust. Shared trust writers serialize updates through the existing OS-released SQLite lock and replace the trust file atomically; concurrent grants and revocations preserve unrelated entries. It neither loads project configuration nor changes the selected profile’s approval mode. Creation requires explicit new-path consent even if an existing parent grant would cover that path. Worktrees share Git history and repository metadata; they are not a sandbox.

Git runs with argument arrays, `shell: false`, bounded output and timeouts. Creation disables hooks, fsmonitor and configured content filters; it does not fetch dependencies, hydrate Git LFS content or initialize submodules. The branch name and destination are generated by core, not supplied as a renderer Git command.

## Storage and identity

For the selected EstaCoda home:

```text
<home>/.estacoda/profiles/<profile>/workspaces.sqlite
<home>/.estacoda-worktrees/<profile>/<operation UUID>/
```

The first path owns names, target records, creation/lifecycle receipts and borrower guards. The second holds project working files. Working files are deliberately outside credential/runtime state so the existing Docker protected-state checks can remain unchanged. Paths use the shared home helper, including an explicitly configured EstaCoda home.

Registry format 3 records managed worktree provenance; ordinary target bindings remain schema version 1. Older readers that do not understand format 3 must refuse the database. Creating a temporary copy never downgrades the database format.

A worktree records its immutable source snapshot, actual working-root identity, source/root directory stamps, Git common-directory identity, worktree registration identity, creation operation, branch and base commit. Validation rejects missing, moved, replaced, symlink-redirected, stale and cross-profile targets. Managed roots and their children cannot be reopened as new local targets to discard this provenance. Alias rename/move does not move a worktree or retarget historical Work.

Runtime tools acquire a core borrower guard before constructing execution resources. The guard stays until environment resources and independent scopes settle. Future Desktop file/diff/PTY consumers must use the same guarded target boundary. PR10 still owns those live interfaces; this PR does not expose a raw terminal or renderer filesystem API.

## Archive and cleanup

**Archive…** is a reviewed metadata transition. It advances the generation and blocks new use, retaining files and the branch. Active work may stop at its next authority validation. Archive can record an unavailable target without following or deleting its missing/replaced path. Alpha has no unarchive or automatic generation-refresh action; start new Work on a valid target.

Physical cleanup is a separate **Remove worktree files…** action. It requires the current generation, an archived core-owned target, verified original directories and Git registration, applicable source/worktree trust, and no borrowers. It refuses tracked, staged, untracked and ignored changes, unknown dirty state and Git removal blockers such as worktree locks. There is no force removal, recursive deletion fallback, branch deletion or source checkout cleanup. Commits remain reachable through the retained branch and historical target references remain in core.

Cleanup does not remove a pre-existing global/parent trust grant. Exact worktree trust records may remain after removal. Core never reuses the removed target’s directory for a new target, and the archived binding stays unavailable.

## Interrupted operations and recovery

Use **Inspect last operation** and **Refresh targets** after a timeout, disconnect or restart. Main persists only the latest profile-scoped operation reference before dispatch. Core reserves effects in its journal before running Git; replaying the same operation does not rerun it. A completed receipt describes lifecycle completion, not an agent Task outcome. Unknown or uncertain receipts do not mean nothing happened.

| Situation | Recovery |
| --- | --- |
| Review expired, source changed, or no committed HEAD | Inspect the source and start a fresh review. |
| Creation interrupted | Inspect the operation and Git’s worktree list. Preserve partial directories and branches; no automatic rollback or duplicate creation is attempted. |
| Cleanup refused | Inspect dirty state, worktree locks, current trust and borrowers. Preserve/commit needed files and settle execution before explicitly requesting cleanup again. |
| Backing path moved or replaced | Leave the historical target unavailable. Restore the original path/registration only after inspecting its identity, or start new Work on a newly selected target. There is no fallback to the source checkout. |
| Borrower process crashed | Retain files. A dead PID alone does not prove its subprocesses or external resources settled. Alpha does not automatically clear these guards; inspected operator maintenance is required before physical cleanup. |
| Git removed files but receipt is uncertain | Inspect both core and Git state. Do not reconstruct the old directory or force a replay to make the receipt look successful. |

The journal is bounded to 1,000 creation attempts and 1,000 lifecycle operations per profile; a full journal fails closed rather than discarding uncertain history. There is no alpha UI for journal compaction, orphan adoption, borrower repair or custom worktree destinations/branch names.

## Host and Docker execution

Target kind is independent of environment policy. Host tools use the verified worktree root. Existing Docker execution binds only that working root and preserves protected-state, credential and network restrictions. The source checkout and shared Git common directory remain outside the container: Git operations needing that external metadata are unavailable inside this single-mount environment. No extra host mount or host fallback is inferred. Docker provisioning/management UI remains outside this Desktop slice.

## Security and validation

The renderer cannot choose Git arguments, a raw destination, profile identity, Main generation or lifecycle operation ID. Review tokens are bridge-local; target operations carry expected core generations. No new execution owner, workspace registry or scheduler is created.

Regression coverage includes real Git creation and cleanup, hook/filter suppression, source/working-root separation, trust revocation, identity replacement, concurrent stores, interrupted process guards, immutable Session bindings, runtime tool writes, IPC rejection, modal keyboard behavior, uncertain receipts and disconnection. Release checks exercise managed worktree files/commands in a real Docker container. Native acceptance creates a worktree through Main/preload/bridge, runs Session/Task work against its binding, and checks restart continuity using a scripted local provider. These checks are distinct from production soak testing and full accessibility certification.
