## Implemented end-to-end workflow

Paths below are relative to `upstream/superagent/`.

### 1. External event → normalized trigger

`src/sources/github.ts:25–38` defines GitHub polling configuration, with a default 60-second poll interval and opt-in observation of unaddressed issues, pull requests, comments and default-branch CI. `githubKind` connects incoming triggers, source-specific scope, channel delivery, context lookup and authorization (`src/sources/github.ts:38–100`).

The declared incoming integration surface includes notifications, subscribed issue/PR discussion, CI changes, and PR merge/close—not merely a manually invoked coding prompt (`src/sources/github.ts:41–43`).

Optional Feishu is wired into application composition and setup (`src/app/runtime.ts:41,100–106`). Its live transport was not exercised.

### 2. Trigger → authorization/admission → assessment

`Engine.receive` is a transactional entry point. It stores a trigger once, fans it out to subscribing tickets and queues primary-thread evaluation, with follow-up ownership exceptions (`src/core/engine.ts:40–49`).

Authorization is implemented in code rather than only described in prompts:

- Source-specific identities; no cross-source identity mapping (`src/policy.ts:1–4`).
- Allowed human explicitly addressing the agent gets explicit strength.
- Other human messages pass source scope/admission-table and follow-up checks.
- Listed bots can only become inferred candidates; unlisted identified bots are rejected.
- Senderless system/CI events require the inferred admission cell and observation mode.
- Inferred acceptance requires `auto` mode and matched enabled rules.

See `src/policy.ts`, **`settingsPolicy`**, particularly its `machineGate`, `gate`, `admitsInferred` and `revalidate` implementations.

Assessment validation requires exactly one assessment per enabled rule; accepted assessments need settled implementation direction, a matching enabled rule and intent evidence. Inferred acceptance outside auto becomes an audited `would_accept` observation (`src/policy.ts:25–64`, **`directionAllowed` / `assessmentOutcome`**).

**Important boundary:** these structural checks are deterministic; whether natural-language evidence truly establishes intent, settled design or a rule match is still model judgment. A required nonempty evidence string is not proof of semantic correctness.

### 3. Assessment → durable decision/ticket

Evaluation keeps per-thread pending/evaluating state and passes a candidate to the assessor (`src/core/evals.ts:105–118`). `Evals.decide`:

- rejects unknown triggers and finished evaluation IDs;
- returns a prior acceptance instead of spawning a second ticket;
- prevents the main session from independently deciding worker-owned follow-ups except to stop;
- rejects inferred acceptance without current auto/rule authorization.

Evidence: `src/core/evals.ts:120–159`, **`decide`**.

Domain mutations are coordinated through one transactional `Engine`, which exposes role-scoped interfaces (`src/core/engine.ts:19–38`).

### 4. Ticket → isolated work directory and persistent session

`DshExecutor` owns a persistent session named **`worker-<ticketId>`**, and ticket-specific workspace directories (`src/executor/dsh.ts:1,22–25`, **`workerSessionId`**).

Workspace setup is an operator-configured prepare command, not an automatic guarantee that every directory is a Git worktree:

- prepare has a ten-minute timeout;
- existing directories count as already prepared;
- failed prepare is not automatically retried;
- an empty failed directory is removed, but a nonempty directory is retained.

Evidence: `src/executor/dsh.ts:27–41,242–258,434–436`, **`prepareDirectory`**.

This is **workspace/session separation**, not demonstrated OS/container isolation. Workers have shell and file-writing tools; do not describe directory isolation as a security sandbox.

Workers receive a restricted tool inventory including files/search, shell/jobs, web, skills, todos and subagents. They do not inherit every host tool; scheduling, profile changes and unrelated sessions are deliberately excluded (`src/app/sessions.ts:55–64`, **`WORK_TOOLS`**).

### 5. Execution, concurrency and human follow-ups

`WorkerSlots` synchronously reserves startup slots before awaits, counts running turns plus surviving shell jobs/subagents, and permits **one extra slot for human follow-ups** (`src/executor/dsh.ts:165–199`).

Launch effects use dynamically available worker slots; pause holds launch and delivery. Delivery effects have a separate limit of four (`src/executor/dsh.ts:226–235`).

This is stronger than merely limiting the number of model turns: background work can retain a ticket’s slot. The executor also contains explicit handling for background work and hand-off (`src/executor/dsh.ts`, **`running`**, **`resumeAfter`**, background-settling and hand-off paths).

### 6. Reports → completion / continued PR ownership → delivery

The core records executor start, delivered/read inputs, ended turns, delivery failure and worker reports. Stale assignment delivery facts are dropped (`src/core/engine.ts:171–207`, corresponding executor-facing methods).

Completion is not simply “the model ended its turn.” A ticket can follow an owned PR/thread; ready reports are coordinated with followed-thread completion and merge/close facts (`src/core/engine.ts:50–67`, **`bindThread` / `threadClosed`**).

The main session can request status, stop, retry stalled tickets, and queue purpose-specific replies. Reply destinations distinguish acknowledgement/answer, attention and result, and result replies have state requirements (`src/core/engine.ts:115–169`, **`requestStatus` / `reply` / `stopTicket` / `retryTicket`**).

Outbound messages use persistent receipts and durable reply effects:

- duplicate IDs are ignored;
- queueing receipt/effect is atomic;
- processing pause or disabled source holds delivery;
- messages preserve per-ticket/conversation order until an earlier message repeatedly fails;
- permanently gone or ignored conversations settle as dropped.

Evidence: `src/app/outbox.ts:18–59`, **`Outbox.send` / `deliver`**.

**Delivery limitation:** the observed path calls `sources.send` before marking the receipt sent. These excerpts do not establish exactly-once external posting across a crash after remote acceptance but before local settlement. Do not equate local deduplication with an end-to-end exactly-once guarantee.

## Persistence, restart and failure behavior

- SQLite stores triggers, dispositions, threads, tickets, decisions, outbox, effects, settings and KV state; WAL and `synchronous=FULL` are configured (`src/app/store.ts:1,45–98`, **`Store` constructor**).
- Supported schema migration is transactional; unsupported versions are rejected and the handle closes on initialization failure (`src/app/store.ts:53–108`).
- Nested savepoint transactions discard rolled-back after-commit callbacks. Durable effects are explicitly distinguished from in-memory callbacks (`src/app/store.ts:141–172`, **`atomic` / `afterCommit`**).
- Runtime locks the state directory before opening the database; compromised lock marks runtime health error and aborts (`src/app/runtime.ts:54–58,90–102`).
- Executor restart reconciliation exists in **`DshExecutor.resume`**, interrupting/reconciling pending/running assignments and stopping lingering work (`src/executor/dsh.ts:520–532`).
- Transient failures use classified provider/network errors, at most three transient attempts and initial 15-second backoff (`src/executor/dsh.ts:29–30,43–54`, **`transient`**).
- Evaluation expiry/requeue, processing-pause deadline extension, and resumption of queued human follow-ups are explicit engine behavior (`src/core/engine.ts:70–89`, **`evaluateDue`**).
- Model-budget wait monitoring is integrated into session health (`src/app/sessions.ts:89–124`, **`Sessions.install`**).

**Caveat:** retry counters shown in the executor are in-memory maps (`src/executor/dsh.ts:208–212`); the excerpt does not establish a durable lifetime retry cap across process restarts.

## Strengths, weaknesses and synthesis implications

**Supported strengths**

1. Coherent, inspectable repository-team workflow spanning source admission through tickets, worker sessions and outbound delivery.
2. Significant deterministic negative/recovery test coverage, successfully executable with prepared dependencies.
3. Explicit background-aware concurrency and human follow-up priority.
4. Durable domain/outbox/effect state and transaction-aware side effects.
5. Real distinction between observed proposals and authorized auto execution.

**Supported boundaries / weaknesses**

1. Research prototype disclaimer, constrained to a one-repository application.
2. Significant host dependence: the bundle is not itself the underlying agent runtime.
3. Model-assessed intent and rules are not semantic authorization proofs.
4. Per-ticket directories do not establish security sandboxing.
5. Prepare failures intentionally require intervention; nonempty partial setup can remain.
6. Exactly-once external delivery and restart-persistent retry ceilings were not established.
7. Current canonical repository origin and current public upstream freshness remain unresolved.

## Discriminating parity scenarios for the synthesis

Run these with matched model, budget, repository fixture, tool permissions and integration fakes:

1. **Admission matrix:** listed/unlisted humans, allowed/disallowed bots, addressed/unaddressed events, and off/observe/auto; assert zero unauthorized worker launches.
2. **Revocation during work:** revoke sender/source/rule authorization while a ticket runs; inspect cancellation, side effects and subsequent resume.
3. **Duplicate/reordered events:** replay a trigger, submit stale assessment, merge a followed PR during a running turn; assert one ticket and correct completion.
4. **Background concurrency:** saturate slots with worker jobs/subagents, then send a human follow-up; observe reservations, extra slot and cleanup.
5. **Crash-window delivery:** crash after remote post acceptance but before receipt settlement; measure duplicates or explicit reconciliation.
6. **Partial workspace setup:** make prepare leave files then fail; verify no silent automatic reuse and clear retry/operator handling.
7. **Restart at transaction/effect boundaries:** commit ticket but stop before launch; interrupt running assignment; test recovery without lost inputs or duplicate work.
8. **Proactivity noise:** mix actionable requests, ambiguous design wishes and CI failures; measure useful work, inappropriate acknowledgements and human interruptions.

These scenarios should be reported as behavioral pass/fail evidence separately from model solution quality and resource cost.
