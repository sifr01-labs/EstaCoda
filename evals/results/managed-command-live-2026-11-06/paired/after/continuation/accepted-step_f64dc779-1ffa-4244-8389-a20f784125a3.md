## 1. Command-completion checks

### Semantics and strengths

**Receipt-bound evidence, not textual success.** The implementation associates calls with receipts by tool-call ID and skips missing-turn receipts or mismatched tool names. Passing requires a successful receipt plus command-level success. The latter requires an allowed call, `result.ok === true`, no possible side effects, and—for managed processes—an exited process with exit code zero and no signal. Non-process results delegate exit interpretation to `settledLocalCommandExit`.
Sources: `src/runtime/command-completion-checks.ts:16-30`, `src/runtime/command-completion-checks.ts:82-85`, `src/runtime/command-completion-checks.ts:157-164`.

**Requirements remain separate.** Check identity incorporates the requirement and working-directory context; results are aggregated so an unresolved instance prevents the same label appearing in `passedRequirements`. An unrelated successful label does not erase an outstanding failure. The overall `passed` result also requires at least one check, avoiding vacuous success.
Sources: `src/runtime/command-completion-checks.ts:107-116`, `src/runtime/command-completion-checks.ts:146-154`.

Existing tests verify that output repair and unrelated success do not settle a failed declared check, while a different implementation using the same requirement can recover it. They also exercise failure exits 127, 139, and 1 and check the feedback names the outstanding requirement.
Sources: `src/runtime/command-completion-checks.test.ts:104-117`, `src/runtime/command-completion-checks.test.ts:185-193`, `src/runtime/command-completion-checks.test.ts:289-299`.

**Freshness is explicitly tracked.** Observed completed file changes and permitted file-write/patch operations invalidate affected checks. Unknown effects remain broad; successful file operations can preserve checks whose declared scopes are unaffected. Managed processes carry their original scope and become stale when affected changes occur. Polling an already-collected process cannot create fresh evidence.
Sources: `src/runtime/command-completion-checks.ts:41-85`.

The passing tests exercise:
- Edits versus unchanged diagnostics: `src/runtime/command-completion-checks.test.ts:119-130`.
- Final managed exits, including exit 1 despite successful log retrieval: `src/runtime/command-completion-checks.test.ts:133-145`.
- Stale exits collected before or after an edit: `src/runtime/command-completion-checks.test.ts:167-183`.

- Conservative unknown/workspace scopes and rejected unsafe scopes: `src/runtime/command-completion-checks.test.ts:439-456`.

**Narrow file predicates receive a deliberate optimization.** A successful literal `test -f` or `test -s` command can retain validity across an unrelated materialized file write, but only with matching completed observation evidence. Compound/generic checks do not receive that shortcut.
Sources: `src/runtime/command-completion-checks.ts:65-74`, `src/runtime/command-completion-checks.ts:89-96`.

**Denied-action recovery has explicit authority boundaries.** Only local denied checks with confirmed non-dispatch and no effects enter the recoverable-denial path. Recovery requires a later, same-turn, same-requirement authorized passing check that remains current; connector and external-effect checks cannot supply that recovery.

Source: `src/runtime/command-completion-checks.ts:119-126`.

### Concrete potential defects and limitations — inferred, not reproduced

1. **Concurrent attempts for one requirement are resolved by collection order.** Every accepted result writes the same identity’s Boolean state. Separate owned processes can therefore update the same requirement as their exits are collected. An older attempt collected last could overwrite a newer attempt’s result—for example, an older passing process could clear a newer failed attempt. Whether this is a defect depends on whether “latest collected proof” or “latest started attempt” is intended.
   Implementation basis: `src/runtime/command-completion-checks.ts:41-46`, `src/runtime/command-completion-checks.ts:82-88`, `src/runtime/command-completion-checks.ts:103-107`.

2. **Unobserved shell mutations remain an intentional coverage limit.** Shell activity only invalidates checks when completed observation evidence reports a change; the implementation explicitly does not infer changes from write-capable risk classification alone. ## 2. Task-result summary

### Semantics and strengths

The function is extractive: it removes fenced code, splits paragraphs, discards presentation-only lines, cleans Markdown, and returns the first nonempty cleaned candidate. It does not synthesize findings from later material. Undefined input or a nonpositive limit yields no summary.
Source: `src/utils/task-result-summary.ts:1-31`.

Cleaning covers headings, rules, pipe-style tables, quote/list prefixes, images and links, selected HTML/autolinks, inline code, emphasis, and strikethrough. It normalizes whitespace, rejects leading ellipsis fragments, and repeatedly strips English or Arabic summary labels.
Source: `src/utils/task-result-summary.ts:34-66`.

Bounding counts Unicode code points for the initial limit and prefix. It prefers a sufficiently long complete sentence, otherwise trims at the last space and appends an ellipsis.
Source: `src/utils/task-result-summary.ts:68-83`.

All four existing tests passed:
- First meaningful paragraph and Markdown link/emphasis removal: `src/utils/task-result-summary.test.ts:5-19`.
- Sentence-boundary truncation: `src/utils/task-result-summary.test.ts:21-25`.
- Leading tail-fragment rejection: `src/utils/task-result-summary.test.ts:27-31`.
- English and Arabic label removal: `src/utils/task-result-summary.test.ts:33-43`.

### Concrete potential defects and missing coverage — inferred, not reproduced

1. **Fallback can exceed `maxChars`.** The fallback takes up to `maxChars` code points and then appends `…` without reserving space. A long unbroken token can therefore produce `maxChars + 1` code points; a limit of one can return a character plus ellipsis.
   Source: `src/utils/task-result-summary.ts:71-83`.
   **Missing coverage:** no-space inputs, tiny limits, and an explicit output-length invariant. The existing bounding test only exercises successful sentence selection: `src/utils/task-result-summary.test.ts:21-25`.

2. **Tail-fragment rejection can be bypassed by removable prefixes.** Ellipsis detection occurs before punctuation and redundant-label stripping. Inputs such as `Summary: …fragment` or `— …fragment` can expose a leading ellipsis only after the rejection check has already run.
   Source: `src/utils/task-result-summary.ts:59-65`.
   **Missing coverage:** combinations of labels/punctuation with fragments; current tests cover these independently: `src/utils/task-result-summary.test.ts:27-43`.

3. **Markdown handling is heuristic rather than comprehensive.** Fenced-code removal recognizes backticks, not tilde fences. Link/image expressions stop at the first closing parenthesis, which can leave residue for URLs containing parentheses. Single-underscore emphasis is not handled by the double-underscore replacement.
   Sources: `src/utils/task-result-summary.ts:13-15`, `src/utils/task-result-summary.ts:43-56`.
   **Missing coverage:** tilde fences, nested-parenthesis URLs, underscore emphasis, tables, HTML, images, quotes, and lists. The only general Markdown test covers a heading, bold text, and a simple link: `src/utils/task-result-summary.test.ts:5-19`.

4. **Unicode handling mixes coordinate systems.** Prefix length is code-point-based, but regular-expression match indices and the sentence minimum comparison use UTF-16 positions. Astral characters can therefore affect the intended minimum-length threshold. Code-point slicing also does not guarantee intact multi-code-point grapheme clusters.
   Source: `src/utils/task-result-summary.ts:69-79`.
   **Missing coverage:** emoji, combining marks, and sentence selection near the threshold.

5. **Nonfinite or fractional limits lack an explicit contract.** Only `maxChars <= 0` is rejected. `NaN`, infinity, and fractional values proceed into comparison/slicing behavior. This is a robustness concern if callers can provide nonvalidated numeric values, not a demonstrated current caller failure.
   Sources: `src/utils/task-result-summary.ts:7-11`, `src/utils/task-result-summary.ts:68-83`.
   **Missing coverage:** invalid numeric limits, undefined/empty input, code-only input, and presentation-only input.
