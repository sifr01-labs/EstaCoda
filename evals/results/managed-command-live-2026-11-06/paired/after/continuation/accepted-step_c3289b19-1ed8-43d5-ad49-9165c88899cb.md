## 1. Command-completion checks

### Implementation semantics

**Success depends on execution evidence, not reassuring output.** Calls are associated with receipts by tool-call ID; missing-turn receipts and mismatched tool names are skipped. A passing check requires both a successful receipt and command-level success: an allowed call, `result.ok === true`, and no possible side effects. For a managed process, the process must have exited with code zero and no signal. Non-process exit interpretation is delegated to `settledLocalCommandExit`.

Sources: `src/runtime/command-completion-checks.ts:16-30`, `:82-85`, `:157-164`.

**Requirements are tracked separately.** Check identity incorporates the requirement and working-directory context. An unresolved instance prevents its label from appearing in `passedRequirements`; an unrelated successful requirement does not erase it. Overall success also requires at least one check, avoiding vacuous success.

Sources: `src/runtime/command-completion-checks.ts:107-116`, `:146-154`.

The tests verify that repairing output or passing an unrelated check does not settle a failed declared requirement, while another implementation of the same requirement can recover it. They also exercise exit codes 127, 139, and 1, and feedback naming the outstanding requirement.

Sources: `src/runtime/command-completion-checks.test.ts:104-117`, `:185-193`, `:289-299`.

**Successful evidence must remain current.** Observed completed file changes and permitted write/patch operations invalidate affected checks. Unknown effects are treated broadly; scoped successful file operations can preserve checks outside the affected scope. Managed processes retain their original scope and can become stale after relevant changes. Polling an already-collected process does not create fresh evidence.

Source: `src/runtime/command-completion-checks.ts:41-85`.

## 2. Task-result summary

### Implementation semantics

The summary function is **extractive**, not a synthesis engine. It removes fenced code, splits paragraphs, discards presentation-only lines, cleans Markdown, and returns the first nonempty cleaned candidate. It does not combine later findings into a new summary. Undefined input or a nonpositive limit yields no summary.

Source: `src/utils/task-result-summary.ts:1-31`.

Cleaning handles headings, rules, pipe-style tables, quote/list prefixes, images and links, selected HTML/autolinks, inline code, emphasis, and strikethrough. It normalizes whitespace, rejects leading ellipsis fragments, and repeatedly strips English or Arabic summary labels.

Source: `src/utils/task-result-summary.ts:34-66`.

Length bounding initially counts Unicode code points. It prefers a sufficiently long complete sentence; otherwise it trims at the last space and appends an ellipsis.

Source: `src/utils/task-result-summary.ts:68-83`.

### Important concerns and missing coverage

Again, these are **inferred from source, not failures reproduced by additional tests**.

1. **Fallback truncation can exceed `maxChars`.**
   The fallback takes up to `maxChars` code points and then appends `…` without reserving space. A long unbroken token can therefore produce `maxChars + 1` code points; a limit of one can yield a character plus ellipsis.

   Source: `src/utils/task-result-summary.ts:71-83`.

   **Missing tests:** no-space input, tiny limits, and a strict output-length invariant. The existing bounding test covers successful sentence selection only (`src/utils/task-result-summary.test.ts:21-25`).

2. **Removable prefixes can bypass tail-fragment rejection.**
   Ellipsis detection occurs before punctuation and redundant-label stripping. Inputs such as `Summary: …fragment` or `— …fragment` may expose a leading ellipsis only after the rejection check has run.

   Source: `src/utils/task-result-summary.ts:59-65`.

   **Missing tests:** labels or punctuation combined with fragments. Current tests cover label removal and fragment rejection separately (`src/utils/task-result-summary.test.ts:27-43`).

3. **Markdown cleanup is heuristic.**
   Fence removal recognizes backticks rather than tilde fences. Link/image expressions stop at the first closing parenthesis, potentially leaving residue for URLs containing parentheses. The double-underscore replacement does not handle single-underscore emphasis.

   Sources: `src/utils/task-result-summary.ts:13-15`, `:43-56`.

   **Missing tests:** tilde fences, nested-parenthesis URLs, underscore emphasis, tables, HTML, images, quotes, and lists. The general Markdown test covers a heading, bold text, and a simple link (`src/utils/task-result-summary.test.ts:5-19`).

4. **Unicode processing mixes code-point and UTF-16 coordinates.**
   Prefix length is code-point-based, while regex match indices and the sentence minimum comparison use UTF-16 positions. Astral characters can affect the intended minimum-length threshold. Code-point slicing also does not guarantee preservation of multi-code-point grapheme clusters.

   Source: `src/utils/task-result-summary.ts:69-79`.

   **Missing tests:** emoji, combining marks, and sentence selection near the threshold.

5. **Unusual numeric limits have no explicit contract.**
   Only `maxChars <= 0` is rejected. `NaN`, infinity, and fractional values proceed into comparison and slicing behavior. This is a robustness concern if callers supply unvalidated limits, not evidence of a current caller failure.

   Sources: `src/utils/task-result-summary.ts:7-11`, `:68-83`.

   **Missing tests:** invalid numeric limits, undefined/empty input, code-only input, and presentation-only input.
