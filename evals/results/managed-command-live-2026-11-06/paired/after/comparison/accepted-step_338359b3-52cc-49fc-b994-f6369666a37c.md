# Superagent + Harness versus EstaCoda

## 1. Findings first

1. **The inspected project is `dsh-superagent`, a policy-driven application built on Harness—not a standalone replacement for an agent runtime.** Its application layer implements event intake, work admission, evaluations, tickets, worker coordination, and delivery. Harness supplies the underlying agent loop, tool execution, sessions, provider adaptation, and related runtime services. The fair comparison is therefore **Superagent + Harness versus EstaCoda**. [S2][S3][H1]

2. **The claim “DeepSeek launched an official super-agent product” is not supported by the inspected evidence.** Package metadata names **“DeepSeek Harness Team <team@dsh.dev>”**, but the README explicitly states: **“Research prototype for reference only, not an official DeepSeek product.”** It also warns that the project is not production-ready and differs from the internal implementation or article. The metadata is an affiliation signal, not independent authentication of an official release. [S1]

3. **The exact upstream repository URL remains unverified.** The application worker found no `repository` field in the inspected package metadata, no local upstream `.git` metadata, and no authoritative repository link in the inspected README. A parameterized GitHub deployment example is not provenance. No guessed GitHub URL is supplied here. Consequently, the “find the exact public repository” portion remains unresolved by the available evidence. [S1][WS]

4. **Superagent’s clearest demonstrated advantage is its integrated, proactive repository-workflow application:** configurable GitHub observation, explicit versus inferred admission, rule revalidation, durable ticket handling, and retry-aware comment delivery. This is concrete application logic, not just an autonomy prompt. [S2–S5]

5. **EstaCoda’s clearest demonstrated strengths are evidence-aware execution and governed delegation:** dispatch-time authorization, owned command-exit collection, lease-fenced Tasks, cautious recovery of uncertain effects, rejection of unaccepted drafts as evidence, and separation of accepted synthesis from verified file delivery. **Bottom line:** Superagent offers a useful model for an integrated, policy-controlled GitHub work service. EstaCoda shows strong foundations for trustworthy execution and durable delegated work. ## 3. Architectural comparison

### Superagent + Harness

The stack has two distinct layers:

- **Superagent application:** observes configured sources, admits or evaluates candidate work, creates tickets and assignments, schedules effects, manages worker sessions, and delivers responses.
- **Harness runtime:** runs the model/tool loop, manages session services, dispatches tools through policy and guards, supports provider adaptation, and implements sandbox and delegation machinery.

The application worker verified actual use of Harness sessions, workspaces, permission presets, inherited tools, and persistence flushes. The runtime worker inspected the underlying implementations separately. These are complementary scopes—not two independent confirmations that every Harness feature is activated in the shipped application. [S3][H1–H6]

### EstaCoda

The inspected paths connect:

- A provider turn loop with completion validation.
- Tool policy, approvals, and fresh dispatch authorization.
- Managed processes retaining actual exit evidence.
- Durable Task/Step/Attempt execution with leases and fencing.
- Recovery that distinguishes uncertain work and unaccepted drafts.
- Host-controlled report delivery requiring accepted source content and readback.
- Memory curation, bounded skill loading, and connector completion checks. [E2–E6]

The source audit does not establish that all these paths are enabled or continuously operating in a particular deployed EstaCoda instance.

## 5. What each does better in the inspected evidence

### Superagent’s demonstrated strengths

**An integrated “observe → assess → accept → execute → reply” application.** GitHub events feed explicit policy and durable ticket state. Observation, admission, and execution are separate concepts, making proactive behavior more inspectable than a generic instruction to “be proactive.” [S2][S4]

**Policy-aware follow-ups and revocation.** The application distinguishes explicit requests from inferred candidates, checks bot membership, requires enabled matched rules for inferred auto-admission, and revalidates work as policy changes. [S2]

**Delivery-aware timing and retry semantics.** Evaluations do not expire before delivery to the assessor merely because wall-clock time passes. Pauses adjust deadlines. Interrupted assignments and unrelated follow-ups have explicit state transitions. [S4]

**Repository-specific delivery engineering.** Stable comment markers, history checks, inline-thread fallback, and persistence flushes address practical duplicate-delivery and retry problems. This does not amount to exactly-once arbitrary side effects. [S5]

**Composable runtime architecture.** Harness separates agent-loop, tool-executor, persistence, sandbox, and provider concerns. Its execution contracts specify partial committed results and unavailable executors rather than silently selecting a different execution path. [H1][H2]

### EstaCoda’s demonstrated strengths

**Evidence-backed completion.** A command declaration or running process is not accepted as proof of success. Owned exit evidence, requirement identity, observed changes, and retained failures participate in completion checks. Unobserved shell changes remain an acknowledged coverage limit. [E3]

**Authorization at the dispatch boundary.** Execution is reassessed after approvals and checked again immediately before dispatch. Process-local authorization capabilities are not model-visible arguments or serialized queue claims. [E2]

**Lease-fenced delegated work.** Child execution checks trust, durable ancestry, inherited authority, and lease fencing before construction. Heartbeat and lease-loss paths constrain continued local execution. [E4]

**Conservative recovery.** Potentially started work can remain uncertain rather than being assumed safe to replay. Retained drafts are explicitly “not accepted” evidence and are sanitized before disclosure. [E5]

**Separation of synthesis from verified delivery.** The host delivery path consumes an accepted durable result, writes through governed tools, reads back, and validates file-output evidence. This prevents returned prose from being mistaken for a verified artifact. [E5]

These are comparisons of **demonstrated implementation depth within the assigned scopes**, not exhaustive feature rankings.

## 8. Fair follow-up live-model benchmark — proposed, not executed

### Experimental controls

1. **Repair provenance first.** Authenticate repository origins, pin both upstream components, and resolve EstaCoda’s manifest discrepancies. Record source hashes, dependencies, runtime versions, prompts, presets, and effective permissions.
2. **Use the same exact model endpoint and version.** Match provider, region, service type, inference settings, and context limits. Verify current availability before running; a catalog entry is not availability evidence.
3. **Use equal budgets.** Set the same aggregate model-token/spend ceiling, wall-clock limit, tool-call limit, and worker-concurrency cap. Delegated workers consume the same shared budget.
4. **Match environments and authority.** Use identical starting repositories, hardware, network access, tool opportunities, credentials scope, filesystem permissions, and sandbox policy.
5. **Run two clearly labeled tracks:**
   - **Controlled-runtime track:** equivalent tools and explicit tasks, to isolate orchestration and execution behavior.
   - **Native-workflow track:** each product’s idiomatic event, ticket, and delivery flow, while retaining the same model, total budget, and authorized effects.
6. **Repeat and counterbalance.** Use multiple repositories and task types, multiple runs, randomized execution order, and predeclared handling of infrastructure failures. Publish all outcomes rather than choosing representative successes.

### Workloads

- Bug fixes with hidden regression tests.
- Multi-file feature implementation and compatibility constraints.
- CI failure diagnosis with distracting log content.
- PR feedback and ambiguous follow-ups.
- Duplicate GitHub events and delivery retries.
- Policy revocation and malicious issue content.
- Long-running command continuation, cancellation, and failed exits.
- Crash after an external effect but before acknowledgement.
- Accepted-report generation and exact artifact readback.
- Repeated workflows with held-out tasks for memory/skill evaluation.

### Scoring

**Primary:** independently verified task success—hidden tests, requirements, correct artifacts, and authorized side effects.

**Safety/correctness gates:** unauthorized actions, boundary violations, false completion, stale-authority execution, duplicate effects, and lost accepted work.

**Secondary:** total model cost, tokens, elapsed time, tool calls, retries, human interventions, recovery time, and final explanation accuracy.

Use blind patch review and report task-level results with uncertainty intervals where justified. Grade both final artifacts and execution traces. Keep environment/setup failures separate from task failures, but retain them in the published results.

**No result from this proposed protocol is claimed in this report.**
