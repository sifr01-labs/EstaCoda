## Implementation-backed findings

### 1. Architecture: application bundle over Harness, not a standalone runtime

The package describes itself as a proactive agent for **one GitHub repository**, optionally listening to Feishu, and declares a DSH bundle manifest and extensive Harness peer dependencies (`upstream/superagent/package.json`, symbols `description`, `dsh.bundle`, `peerDependencies`).

The actual composition root is `Runtime`, connecting:

- `Store`, `Engine`, and `Settings`;
- `SourceRegistry`, `MasterAssessor`, and `DshExecutor`;
- `Effects`, `Outbox`, `Passes`, `Sessions`, and `Prompts`.

It obtains session controllers, tools, permissions, subprocesses, workspace services, and other facilities from Harness/Cordis imports rather than independently implementing the underlying runtime (`upstream/superagent/src/app/runtime.ts:1–57`, `Runtime`).

`Runtime` creates a private state directory, takes a `proper-lockfile` lock **before opening SQLite**, records lock compromise as runtime health failure, and aborts its lifetime signal. Constructor failure closes the store and releases the lock (`upstream/superagent/src/app/runtime.ts:89–104`, constructor failure handler near the end of the inspected constructor).

**Comparison implication:** credit Superagent for its application-level orchestration and team workflow; attribute underlying execution capabilities to its Harness host unless independently established.

### 2. Authorization: deterministic gates plus model assessment

There are distinct authorization layers:

- `settingsPolicy().gate` handles source-local sender identities, addressed messages, source observation/admission settings, bot admission, and follow-ups.
- Listed humans addressing the agent receive explicit strength; inferred admission is constrained by evaluation mode.
- `assessmentOutcome` requires exactly one assessment for every enabled rule, refuses unsettled direction and acceptance with no matched rule, and requires `intent_evidence`.
- Inferred acceptance outside `auto` mode becomes an ignored, audited **`would_accept`** proposal.
- `settingsPolicy().revalidate` checks whether a mandate still holds under current source scope, sender/bot lists, admission strength, mode, and enabled rules.

References: `upstream/superagent/src/policy.ts:26–61` (`directionAllowed`, `assessmentOutcome`), `:167–245` (`settingsPolicy`, `gate`, `revalidate`).

This is stronger evidence than a prompt-only instruction to “act responsibly.” However, these gates **do not demonstrate resistance to all prompt injection or establish an operating-system security boundary**.

### 3. Work lifecycle and recovery

The inspected tests exercise a concrete progression: trigger → assessment → decision → ticket with mandate → assignment → worker inputs/reports.

Implemented safeguards include:

- Deduplicated intake and source filtering.
- Atomic acceptance behavior: if ticket preparation throws, no ticket, subscription, decision, or acknowledgement is committed.
- Rejection of stale assessment decisions.
- Evaluation timeout retries twice, then an unavailable decision.
- Assignment-aware input delivery and rejection of late reports.
- Resume under a revalidated mandate; human-stopped work remains stopped.
- Explicit retry of failed or delivery-stalled work.

Implementation references:

- `upstream/superagent/src/core/tickets.ts:104–113` — attachment/resume mandate checks.
- `:165–178` — `retry`.
- `:249–269` — paused/idempotent resume and revalidation.
- `upstream/superagent/src/executor/dsh.ts:207–236` — `DshExecutor`, worker slots and effect handlers.
- `:238–280` — workspace preparation, queued launches, stale-assignment protection.

`DshExecutor` bounds launches by configured worker slots. A failed prepare command is deliberately **not automatically retried**, because a partially populated directory must not silently count as successfully prepared. Launch effects have retry settings; paused execution sets launch/delivery concurrency to zero.

### 4. Integrations

`SourceRegistry` exposes common source scope, channel delivery, and context reading. Delivery can return `sent`, `gone`, or `waiting` (`upstream/superagent/src/sources/registry.ts:95–98`, `:116`; source contracts at `upstream/superagent/src/sources/kind.ts:53`, `:68–78`).

Feishu implements live-event consumption, history backfill, and subscribed-thread polling. Backfill occurs before cursor advancement; thread polling recovers replies missed by the live stream (`upstream/superagent/src/sources/feishu-loops.ts:1`, `:146–164`, `:217–219`).

`Runtime` wires GitHub pull-end notices back through the outbox (`upstream/superagent/src/app/runtime.ts`, constructor event handler using `pullEndNotices`).

**Limit:** these integration implementations were inspected, not exercised against real GitHub or Feishu accounts. No connectivity, credential validity, delivery latency, or API compatibility is established.

### 5. Attention management is represented in domain state

This is not merely README philosophy:

- Worker reports maintain an open attention question and can clear or replace it.
- A replaced/cleared question withdraws its pending unsent reply.
- Attention replies must match the ticket’s **currently open question**.
- Answers/results have separate authorization conditions.
- Automatic input is held while the worker waits for a person.

References:

- `upstream/superagent/src/core/assignments.ts:94–121`.
- `upstream/superagent/src/core/replies.ts:46–47`, `:75–86`.
- `upstream/superagent/src/core/tickets.ts:238–244`.

Executed tests include holding automated input while blocked/failed (`upstream/superagent/tests/core-engine.spec.ts:965`), releasing the wait on human input/report/retry (`:979`), and refusing answers/results/attention outside their allowed state (`:1026`, `:1278`).
