## Implementation findings

All abbreviated `tests/...` references below are relative to `upstream/superagent/`.

### 1. GitHub and Feishu intake

**Strengths**

- GitHub normalizes issues, pull requests, comments, inline reviews and CI transitions into domain triggers. URL parsing rejects other repositories, review triggers retain location/context, and mention matching uses explicit boundaries.
  Source: `upstream/superagent/src/sources/github-trigger.ts:1–17,23–61`.
- GitHub polling maintains retry state alongside cursor progress. Its implementation distinguishes deleted issues (`410`) from `404`, which can indicate revoked access to a private repository.
  Source: `upstream/superagent/src/sources/github.ts:157`, `pollNotifications:297–344`.
- Feishu normalizes direct messages and mentions, suppresses its own bot messages, and derives deterministic trigger IDs across live/history reads. Live consumption, backfill and name refresh run separately.
  Sources: `upstream/superagent/src/sources/feishu-trigger.ts:17–43`; `upstream/superagent/src/sources/feishu-loops.ts:1–19`.

**Negative/recovery cases executed and passed**

| Case | Test reference |
|---|---|
| Failed stream preserves its cursor while other streams continue | `tests/sources.spec.ts:1269` |
| Failed Feishu history read preserves the chat cursor | `tests/sources.spec.ts:1112` |
| Consumer exit triggers restart and subsequent readiness | `tests/sources.spec.ts:1176` |
| Failed→passed→failed CI transitions receive distinct identities | `tests/sources.spec.ts:1357` |

**Gap:** human/bot classification is not proof of human identity. GitHub explicitly acknowledges that automation using an ordinary user account counts as human; prompts identify those automated accounts.
Source: `upstream/superagent/src/sources/github-trigger.ts:42–47`.

### 2. Authorization and proactive rules

**Strengths**

- Authorization uses source-specific identities: a Feishu ID does not authorize a GitHub login with the same text.
- Gates distinguish explicit, inferred and ignored admission, with configurable admission cells and special handling for bots and follow-ups.
- Inferred acceptance requires automatic mode, enabled matched rules, settled implementation direction and intent evidence. Non-auto observation records a proposal rather than launching inferred work.
- Mandates are revalidated against current source scope, admission strength, rule enablement and proactive mode.

Sources: `upstream/superagent/src/policy.ts:25–57,167–239`; `upstream/superagent/tests/policy.spec.ts:54–84,109–162,205–224`.

**Important qualification:** “only allowlisted users can ever create work” would be inaccurate. Configuration can explicitly admit unlisted addressed senders, and participating threads have follow-up semantics. Configured behavior must be distinguished from defaults.
Sources: `upstream/superagent/src/policy.ts:197–209`; `upstream/superagent/tests/policy.spec.ts:109,137–148`.

**Gap:** the proactive mandate also relies on natural-language instructions requiring independent verification that work is small and bounded. Semantic scope judgment remains model-dependent even though gate and rule bookkeeping are deterministic.
Source: `upstream/superagent/src/executor/dsh.ts:88–94`, `mandateInstructions`.

**Discriminating passing cases:** refusal of proactive acceptance without matched rules and duplicate acceptance; enforcement of admitted rules; mandate invalidation when admission strength falls.
Sources: `tests/core-engine.spec.ts:899,919`; `tests/policy.spec.ts:153`.

### 3. Tickets, assignments and recovery

**Strengths**

- Tickets represent work separately from execution attempts. Retry/relaunch uses assignments rather than replacing the work item's history.
- Recovery distinguishes messages delivered to an inbox from messages actually consumed in a worker step.
- Restart removes stale queued copies before delivering a replacement assignment.
- Launch authorization is checked again immediately before worker delivery.

Sources: `upstream/superagent/src/core/assignments.ts:90–99`; `upstream/superagent/src/executor/dsh.ts:440–468`.

**Negative/recovery cases executed and passed**

| Case | Test reference |
|---|---|
| Person-stopped ticket cannot be retried after a failed report | `tests/core-engine.spec.ts:1271` |
| Restart/retry preserves messages no worker step consumed | `tests/core-engine.spec.ts:1540–1585` |
| Recovery handles already-running work, subagents and interrupted inbox delivery | `tests/runtime-concurrency.spec.ts:529,597,670–710` |

### 4. Execution isolation and application-versus-host attribution

**Application responsibilities**

- Per-ticket execution metadata and workspace preparation.
- Stable per-ticket worker sessions and assignment delivery.
- Account-oriented Git/CLI environment overrides, shims and command guardrails.
- Worker-slot accounting, cancellation and background-work ownership.

Sources: `upstream/superagent/src/executor/dsh.ts:96–110,171–207,237–268,430–468`; `upstream/superagent/src/infra/environment.ts:17–18,38–57,86–115`.

**Security limitation:** the implementation expressly describes these as **default-path guardrails, not an OS-level security boundary**, because workers run under the operator's OS user. Separate directories/sessions should not be scored as container, VM or hostile-code isolation.
Source: `upstream/superagent/src/infra/environment.ts:1–5`.

**Harness attribution:** the application consumes DeepSeek Harness agent, session, persistence, subprocess and tool/permission infrastructure. It orchestrates those services rather than independently implementing the entire execution runtime. Credential-shaped environment stripping by the subprocess runtime is specifically host behavior.
Sources: `upstream/superagent/package.json` (`peerDependencies`); `upstream/superagent/src/infra/environment.ts:127–129`; `upstream/superagent/src/executor/dsh.ts:440–441`.

### 5. Retries and failure recovery

**Strengths**

- Launch handling distinguishes transient failures from preparation failures.
- Preparation failures deliberately **do not automatically retry**, avoiding automatic reuse of a partially prepared directory.
- Durable effects support delayed retries, bounded backoff, queue ordering and health reporting.
- Recovery considers background jobs, subagents, shutdown and replacement assignments—not just the foreground model turn.

Sources: `upstream/superagent/src/executor/dsh.ts:270–284`; `upstream/superagent/src/app/effects.ts`, `Effects`; `upstream/superagent/tests/effects.spec.ts:29–35,85–105,137–150`.

**Negative/recovery cases executed and passed**

| Case | Test reference |
|---|---|
| Transient launches retry three times; failed preparation fails immediately | `tests/runtime.spec.ts:1575` |
| Shutdown retains interrupted queued effects for restart | `tests/effects.spec.ts:105` |
| Failed durability barrier retries without another delivery | `tests/delivery.spec.ts:89` |
| Duplicate/out-of-order/previous-step retry events cannot overwrite active retry state | `tests/retry-health.spec.ts:73` |

**Limit:** simulated restart and interruption cases provide meaningful regression coverage, not proof against every process-kill, storage-corruption or remote-service failure mode.

### 6. Result delivery and human attention

**Strengths**

- Replies have purpose-specific gates: results require ready/finished work; attention must match the current question; answers require an eligible human message.
- Deterministic message IDs and stored receipts suppress duplicate enqueueing.
- Outbox receipts and queued effects are created atomically.
- Disabled/uninstalled sources defer delivery; permanently gone channels settle rather than retrying indefinitely.
- Replaced or cleared human questions withdraw pending unsent attention messages.
- Blocked/failed reports suppress automatic inputs until appropriate intervention.

Sources: `upstream/superagent/src/core/replies.ts:20–24,64–91`; `upstream/superagent/src/app/outbox.ts:27–50`; `upstream/superagent/src/core/assignments.ts:99–132`.

**Negative/recovery cases executed and passed**

| Case | Test reference |
|---|---|
| Pending messages wait during pause and send after resume | `tests/outbox.spec.ts:17` |
| Missing source registration defers delivery until registration | `tests/outbox.spec.ts:30` |
| Invalid question/result combinations and invalid referenced people are rejected | `tests/core-engine.spec.ts:822` |
| Current-question, reported-answer and ready-result requirements are enforced | `tests/core-engine.spec.ts:1026` |
| Repeated answer/result requests are suppressed | `tests/core-engine.spec.ts:1278` |

**Limit:** application-level deduplication is not unconditional exactly-once remote delivery. The inspected sequence sends externally and then settles the local receipt, leaving a potential crash window between those operations.
Source: `upstream/superagent/src/app/outbox.ts:48–50`.
