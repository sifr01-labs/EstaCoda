## Source findings and inferred guarantees

### 1. Cancellation is durable before local abort

`TaskScheduler.cancelTask()` first calls `cancelTaskInStore()`, then aborts matching local executions (`src/tasks/task-scheduler.ts:424-437`).

The helper performs cancellation in `atomicWrite`:
- Already-terminal tasks return unchanged.
- Pending/ready/operator-wait steps become cancelled.
- Queued attempts and unleased operator-wait attempts become cancelled.
- Active attempts receive a cancellation request.
- The task becomes cancelled and a task-state event is appended.

Evidence: `src/tasks/task-operator-service.ts:781-850`.

**Inference:** Local `AbortSignal` delivery is not the sole cancellation barrier. Even an executor ignoring abort should encounter durable task/lease state when attempting settlement. Cancellation does not imply immediate termination of external work or reversal of executor side effects.

### 2. Launch and settlement both defend against cancellation races

Execution checks `controller.signal.aborted` before calling the executor; an already-aborted launch is converted to a cancelled settlement (`src/tasks/task-scheduler.ts:1144-1155`). The launch-microtask test directly validates this local race.

Settlement checks terminal task status, the current lease's cancellation marker, and an explicit cancelled outcome before accepting success; any of those conditions route to cancellation settlement (`src/tasks/task-scheduler.ts:1330-1363`).

Cancellation settlement:
- Rechecks ownership/fencing/expiry while allowing the cancellation marker.
- Marks the attempt cancelled.
- Cancels a nonterminal step.
- Releases the exact fenced lease.
- Appends the cancellation event.

Evidence: `src/tasks/task-scheduler.ts:1687-1714`.

**Inference:** A late successful executor response arriving after durable cancellation should be converted to cancellation rather than accepted. This conclusion follows from source control flow, not from the cooperative-cancellation test alone.

### 3. Lease validation is precise but not a complete attempt-state predicate

`#assertCurrentLease()` rejects:
- Missing task, attempt, or lease.
- Owner mismatch.
- Fencing-token mismatch.
- Lease expiry, including equality with the current time.
- A cancellation request when cancellation is not allowed.

For ordinary settlement it additionally rejects terminal tasks. Evidence: `src/tasks/task-scheduler.ts:1956-1978`.

**Important limit:** This helper does **not itself** check attempt status, that the attempt is the latest attempt, active plan revision, or attempt-to-task/step relationships. Successful settlement adds a `currentStep.status === "running"` check (`src/tasks/task-scheduler.ts:1465-1467`), but still relies on surrounding invariants/result-service validation for the full attempt provenance/state predicate.

This is **not a demonstrated bypass**: normal paths release leases when settling, and a newer fence invalidates an older execution. It is an audit boundary that the result-service investigator should explicitly reconcile rather than assuming this helper independently establishes every attempt invariant.

### 4. Cancellation after lease expiry becomes reconciliation, not stale acceptance

Cancellation settlement still requires an unexpired current lease. When a lease-loss error occurs and the current lease contains cancellation, execution tries fenced cancellation settlement; failure of that attempt is counted as lease loss (`src/tasks/task-scheduler.ts:1190-1202`).

Abandoned-attempt recovery considers active attempts whose leases are absent/expired. For a terminal task it marks the attempt cancelled, releases any remaining lease, cancels the nonterminal step, and records cancellation (`src/tasks/task-scheduler.ts:836-864`).

**Inference:** Task cancellation can precede durable cleanup of running attempt/step state. Expired executors cannot use cancellation cleanup as permission to publish; cleanup is deferred to reconciliation.

### 5. Result publication is inside the settlement transaction

The scheduler:
1. Prepares results with expected lease owner and fencing token (`src/tasks/task-scheduler.ts:1421-1437`).
2. Enters `store.atomicWrite`.
3. Revalidates lease/task and requires a running step.
4. Calls `resultService.publishPrepared(preparedResults, store)`.
5. Records usage, completed attempt/step/task state, releases the lease, and appends completion events.
6. Finalizes prepared content after the transaction; on failure, discards prepared content.

Evidence: `src/tasks/task-scheduler.ts:1463-1535`.

A result-service `"result-fence-lost"` error is translated into scheduler lease loss, rather than accepted as successful publication (`src/tasks/task-scheduler.ts:1438-1441`, `src/tasks/task-scheduler.ts:1477-1484`).

Failure diagnostics use the same basic boundary: prepare first, then `#assertCurrentLease(..., false)` and publication inside an atomic write (`src/tasks/task-scheduler.ts:1729-1760`).

**Measured support:** The publication-failure and invalid-post-publication-write tests demonstrate rollback of visible result records/events in two concrete failure scenarios. They do not exhaust every cancellation/publication interleaving or physical-content cleanup failure.

## Cross-subsystem composition argument and remaining risk

**Testable composition argument:** If result preparation is non-authoritative, `publishPrepared(..., store)` participates in the supplied store transaction, and result-service fence validation rejects stale/cancelled/terminal-attempt provenance, then scheduler cancellation and publication compose:

- Cancellation committed first → settlement observes cancellation/terminal state and cannot publish success.
- Settlement committed first → later cancellation returns the already-terminal task unchanged.
- Cancellation/fence change between preparation and publication → the transaction-time scheduler/result-service checks reject publication.

Scheduler-side evidence is `src/tasks/task-operator-service.ts:806`, `src/tasks/task-scheduler.ts:1350-1358`, and `src/tasks/task-scheduler.ts:1463-1535`. Full confirmation of the result-service conditions belongs to the other investigator.

**Concrete coverage risk:** The inspected cancellation test's name overstates its demonstrated behavior. It does not test an executor that ignores abort and later returns a successful result. This leaves the central cancellation-versus-late-success composition dependent on source reasoning.

Recommended existing-test extension for the synthesizer to record—not implemented here:

1. Start an executor whose resolution is controlled independently of abort.
2. Commit scheduler cancellation.
3. Resolve the executor with success and result content.
4. Assert cancelled task/step/attempt, no lease, no results, no result-recorded/completion events, and no readable result handle.
5. Separately force cancellation/fence replacement after preparation but before publication and assert rejection plus cleanup.

**Overall scheduler assessment:** No acceptance bypass was demonstrated. The executed suite supports cancellation, pre-launch suppression, expired-lease rejection, and atomic result rollback. Stronger claims about noncooperative late success and every attempt-state/provenance boundary remain inferred or require the complementary result-service evidence.
