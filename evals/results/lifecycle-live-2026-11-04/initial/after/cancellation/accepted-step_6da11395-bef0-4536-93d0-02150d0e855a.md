## Findings

### 1. Preparation and publication both enforce a supplied lease fence

`RecordTaskResultInput.expectedLease` is explicitly optional and documented as the scheduler settlement fence (`src/tasks/task-result-service.ts:33–46`).

During preparation:

- The service resolves the task, attempt, and effective step.
- A supplied attempt must belong to the task.
- A supplied fence requires an attempt.
- The service validates the lease before preparing the result.
- Attempt/step/task relationships are checked.
- Accepted results must match the step’s result policy.

References: `src/tasks/task-result-service.ts:338–361`.

At publication, `#validatePreparedEntries` repeats the task/attempt/step relationship checks and lease validation against the store passed to publication, rather than trusting preparation-time state (`src/tasks/task-result-service.ts:393–417`). `publishPrepared` invokes this validation before inserting metadata or journal events (`src/tasks/task-result-service.ts:217–247`).

The fence helper rejects when any of these conditions holds:

- Lease is absent.
- Owner differs.
- Fencing token differs.
- Lease expiry is at or before the service clock.
- `cancellationRequestedAt` is present.

It throws `TaskResultContentError` with code **`result-fence-lost`** (`src/tasks/task-result-service.ts:684–698`).

**Interpretation:** preparation-time permission is not sufficient to publish a fenced result. Cancellation or lease replacement before publication is rechecked.

**Qualification:** these are conditional guarantees. The service performs this check only when `expectedLease` is supplied.

### 2. Existing test directly measures the prepare/cancel/publish race

The test at `src/tasks/task-result-service.test.ts:318–371`:

1. Creates a running task, step, and attempt.
2. Acquires a scheduler-owned attempt lease.
3. Prepares result content with the expected owner/token.
4. Calls `requestAttemptCancellation`.
5. Attempts publication inside `store.atomicWrite`.
6. Expects **`result-fence-lost`**.
7. Discards the preparation.
8. Verifies no result metadata exists and the prepared content file is absent.

The decisive assertions are at `src/tasks/task-result-service.test.ts:364–370`.

**Measured outcome:** this named test passed in the executed suite.

**Limit:** this test exercises the cancellation flag, not a matrix of owner mismatch, token mismatch, missing lease, expiry, changed attempt generation, or terminal task status.

### 3. Publication is transactional; prepared bodies are not yet published results

`record()` prepares content, performs publication within `store.atomicWrite`, finalizes on success, and discards on error (`src/tasks/task-result-service.ts:166–176`).

`prepare()` writes and verifies bodies while keeping result metadata absent; it also rejects duplicate identities within the batch (`src/tasks/task-result-service.ts:179–210`).

`publishPrepared()` inserts result metadata and `result-recorded` events. Its contract requires the caller to settle Attempt/Step/Task in the **same transaction**, then finalize after commit (`src/tasks/task-result-service.ts:213–247`).

Cleanup distinguishes committed from uncommitted bodies: `discardPrepared()` uses committed metadata to preserve a body if the transaction actually succeeded (`src/tasks/task-result-service.ts:258–264`, `src/tasks/task-result-service.ts:469–481`).

The existing atomic-batch test forces a duplicate event identity on the second publication, expects transaction failure, discards the batch, and verifies:

- No result metadata.
- No `result-recorded` events.
- Neither body file remains.

Reference: `src/tasks/task-result-service.test.ts:293–316`.

**Measured outcome:** that test passed. The suite also reported passing cases for event-persistence rollback and preparation recovery.

### 4. Acceptance is more than “the body was stored,” but the service is not the whole acceptance boundary

The service defaults disposition to **`accepted`** and applies step result-kind policy to accepted results (`src/tasks/task-result-service.ts:360–372`). Publication repeats policy validation and enforces an aggregate byte budget per step and disposition (`src/tasks/task-result-service.ts:417–437`).

The scheduler prepares successful results only when `acceptanceFailure` is absent and supplies the lease owner/token (`src/tasks/task-scheduler.ts:1421–1435`). A result-fence error is translated into `TaskSchedulerLeaseLostError` (`src/tasks/task-scheduler.ts:1436–1439`).

Primary-result selection is a separate consumer gate: it selects an available, accepted result associated with the active revision’s synthesis step (`src/tasks/task-primary-result.ts:27–38`). Request-completion accounting likewise requires available accepted results and completed worker steps (`src/tasks/task-primary-result.ts:5–20`).

**Important distinction:** storing an available diagnostic result does not make it an accepted primary answer. Conversely, direct service callers can default to accepted disposition; the service does not itself reproduce all scheduler acceptance logic.

### 5. Terminal cancellation protection is principally at the scheduler caller boundary

Immediately before publication, the scheduler opens an atomic transaction and:

- Calls `#assertCurrentLease(..., false)`.
- Requires the current step to remain `running`.
- Rejects replacement of checkpointed worker-session or trajectory identities.
- Publishes prepared results.
- Updates attempt and step completion.
- Updates task settlement state.
- Releases the lease, failing if release does not match.

References: `src/tasks/task-scheduler.ts:1463–1496`, `src/tasks/task-scheduler.ts:1497–1513`.

After transaction success it finalizes prepared bodies; on error it discards them (`src/tasks/task-scheduler.ts:1531–1546`).

`#assertCurrentLease` checks task/attempt existence, lease presence, owner, fencing token, expiry, and—when cancellation is disallowed—the cancellation-request flag. It then rejects terminal task status with `TaskSchedulerCancellationError` (`src/tasks/task-scheduler.ts:1956–1978`).

**Source-derived composition invariant:**

> Successful scheduler publication must pass both the scheduler’s nonterminal-task/current-lease/running-step gate and the result service’s publication-time lease gate inside the settlement transaction.

This is a concrete reason the boundaries can compose. The measured service cancellation test supports the publication-time half of this invariant; this worker did **not** execute scheduler tests to measure the whole composition.

### 6. The result service is not an unconditional terminal-state or generation firewall

The inspected service preparation/publication validation checks task existence and relationships, but does not explicitly reject terminal task, step, or attempt status (`src/tasks/task-result-service.ts:338–361`, `src/tasks/task-result-service.ts:393–437`).

Its lease assertion checks owner/token/expiry/cancellation, not attempt status, active plan revision, latest attempt number, or an independent generation field (`src/tasks/task-result-service.ts:684–698`).

The inspected SQLite `recordResult()` adds transaction/profile/task-ownership and size/display-summary checks, then inserts the result. It does not add an explicit terminal-status or lease check in that method (`src/tasks/sqlite-task-store.ts:1001–1037`).

**Precise fence distinction:**

| Fence | Inspected result-service behavior |
|---|---|
| Attempt identity | Resolves the specified attempt and checks task/step relationships. |
| Lease ownership | Checked when `expectedLease` is present. |
| Lease generation/token | Expected fencing-token equality checked when supplied. |
| Lease expiry | Checked when supplied. |
| Cancellation flag | Checked when supplied, including again at publication. |
| Terminal task/step/attempt | No explicit service validation observed. Scheduler adds terminal-task and running-step gates. |
| Latest attempt / active-plan generation | No explicit service check observed. No independent service generation field was observed. |

**Do not infer** that a token necessarily proves newest-attempt or newest-plan membership from this worker’s evidence. Lease acquisition/reassignment and complete scheduler retry/revision behavior were not audited here.

### 7. Read and export gates do not require a noncancelled task or accepted disposition

`readText()` requires:

- Existing task and session authorization.
- Matching result/task identity.
- Result status `available`.
- Unexpired retention.
- Text-readable content.
- Integrity-verified body and valid UTF-8.

Reference: `src/tasks/task-result-service.ts:528–565`.

`readPage()` delegates to `readText()` and adds bounded Unicode paging and primary-result metadata (`src/tasks/task-result-service.ts:498–525`). `preview()` applies available/expiry/session gates and verifies content (`src/tasks/task-result-service.ts:489–497`). Body reads verify regular-file/no-symlink properties, length, read stability, and content hash (`src/tasks/task-result-service.ts:585–627`).

Neither `readText()` nor the inspected preview gate requires task status to be nonterminal or disposition to be accepted. Thus **cancellation does not itself revoke previously published retained output**, and diagnostic output remains inspectable subject to normal authorization.

The read tool labels diagnostic output as incomplete and not accepted as the successful step result (`src/tools/task-result-tools.ts:74–85`). Its diagnostic-label test passed (`src/tools/task-result-tools.test.ts:60`).

The export tool:

- Is registered only with artifact storage and an export root.
- Calls the same authorized `readText()` method.
- Writes the exact text into a private Markdown export.
- Records disposition in artifact metadata.

References: `src/tools/task-result-tools.ts:107–179`.

Existing tests for exact authorized export and unavailable/unsafe-filename handling passed (`src/tools/task-result-tools.test.ts:116`, `src/tools/task-result-tools.test.ts:159`). Missing/unauthorized read handling also passed (`src/tools/task-result-tools.test.ts:83`).

**Qualification:** export does not independently require accepted disposition or a noncancelled task. That is consistent with inspection access, but export success must not be treated as proof of successful task settlement.

## Concrete cross-subsystem risk for synthesis

**Risk: an alternate publication caller omits `expectedLease` or treats exportability as acceptance.**

The service’s fence is optional, and its task-state validation is weaker than the scheduler’s publication transaction. A caller using `record()`/`prepare()` without `expectedLease` does not receive cancellation/owner/token/expiry rejection from the service. The inspected SQLite insertion method does not supply that missing fence. An available result is then readable/exportable without an accepted-disposition or nonterminal-task requirement.

Supporting references:

- Optional fence: `src/tasks/task-result-service.ts:33–46`.
- Conditional fence validation: `src/tasks/task-result-service.ts:345–351`, `src/tasks/task-result-service.ts:403–407`.
- No explicit terminal gate in service validation: `src/tasks/task-result-service.ts:393–437`.
- Persistence boundary: `src/tasks/sqlite-task-store.ts:1001–1037`.
- Read/export boundary: `src/tasks/task-result-service.ts:528–565`, `src/tools/task-result-tools.ts:140–175`.

This is a **source-derived boundary risk, not a demonstrated production exploit or an executed failing test**. It identifies a contract to preserve: scheduler-originated settlement must always carry the lease fence and publish within the scheduler’s guarded transaction; downstream consumers must distinguish readable output from accepted completion.
