# dsh-superagent + Harness versus EstaCoda: source-and-test benchmark

## 1. Identification correction and bottom line

**The comparison target is the complete `dsh-superagent` + Harness stack, not an application or instruction bundle alone versus EstaCoda’s entire runtime.** Bundle-level instructions, workflows, and tools must be separated from runtime-level execution, authorization, persistence, recovery, and accounting.

However, **the external project’s canonical repository URL and exact identity could not be verified from accepted worker evidence**. The `superagent-application` and `deepseek-harness-runtime` research scopes both failed and supplied no accepted results. Consequently, this report does not substitute a similarly named project, invent repository URLs, or treat diagnostic drafts as verified research. Live-web verification of launch date, latest release, current maintenance, and current availability was not performed.

The useful, supported findings are:

- **EstaCoda is an implemented runtime, not merely a prompt bundle.** Inspected source includes a bounded provider/tool loop, dispatch authorization, durable task orchestration, lease-based recovery, access-controlled results, estimated-spend reservations, and governed skill updates. [E1–E7]
- **Two bounded offline test runs passed 249 unique tests across 16 files, with zero failures.** They establish selected operational invariants—not coding ability, deployment readiness, or superiority over another system. [T1–T2]
- **No comparative winner is established.** Neither external source inspection nor accepted external test receipts are available, and no matched live-model experiment was performed.
- **The immediate engineering opportunity is validation across boundaries:** combined recovery/security scenarios, dependency-readiness checks, spend reconciliation, and measured skill-learning gains. These are evidence gaps and recommended evaluations, not demonstrated missing implementations.

## 5. Security and durability: strengths and tradeoffs

### Authorization is not the same as containment

Source stores dispatch capabilities in process-local WeakMaps rather than serialized/model-visible records. Tool execution includes exact-call approval checks and validates authorization immediately before dispatch. Tests cover revocation and approval binding. [E2]

This supports a concrete claim about authorization provenance and stale-grant rejection. It does **not** establish universal sandboxing, safe arbitrary host execution, or resistance to every filesystem, network, browser, or container escape.

**Tradeoff:** precise authorization can prevent unauthorized dispatch, while containment must separately limit what an authorized but compromised operation can do. Docker and full isolation boundaries were not evaluated.

### Durable recovery is not exactly-once external execution

The scheduler uses leases, renewal, and lease-loss aborts. Abandoned-attempt recovery records interruptions and explicitly preserves uncertainty about potential side effects. [E3]

**Tradeoff:** retaining uncertainty is safer than assuming a failed process did nothing, but it can require reconciliation or operator review. Persistence alone does not make an external API call or shell side effect exactly-once.

Delegation tests also demonstrate authority narrowing, budget constraints, restart preservation, and partial synthesis. These are meaningful deterministic checks, not proof of resilience under every production outage.

### Result durability includes integrity and access checks

Result reads check session authorization, task/result association, availability, and file integrity. Executed tests include tampering, symlink rejection, paging after restart, and retention behavior. [E4]

**Tradeoff:** these checks strengthen the result service boundary, but do not establish backup restoration, disaster recovery, or all multi-host storage behavior.

### Spending controls retain uncertain liabilities

The provider-spend controller reserves and settles estimated monetary amounts and can retain dispatched reservations whose outcome is unknown. Tests cover concurrency and cross-process oversubscription protection. [E5]

**Tradeoff:** conservative holds protect budgets but may reduce available capacity pending reconciliation. These controls are not verified against provider invoices; pricing freshness and actual billed spend remain unmeasured.

### Learning is governed, not unrestricted

Generic candidate promotion requires approval. The skill path also permits a narrowly gated automatic instruction-only update mode with trust/risk checks, evaluation evidence, base-content checks, snapshots, and authority revalidation. [E7]

It would be inaccurate to claim either unrestricted self-modification or mandatory human approval for every possible skill update.

**Tradeoff:** constrained promotion improves control, but safe promotion does not establish that learned instructions improve coding outcomes. That requires separate held-out evaluations.

## 8. Fair, reproducible performance benchmark plan

**This plan has not been executed.**

### A. Establish identities and comparison arms

1. Verify canonical repositories through authoritative project evidence.
2. Record exact application, Harness, and EstaCoda commits, dependency locks, local modifications, and container/environment digests.
3. Test the **complete external stack** against EstaCoda as the primary product comparison.
4. Where technically valid, add bundle/runtime ablations to explain contributions. Do not treat those ablations as substitutes for the complete-stack result.

### B. Hold model and resources constant

Use the same exact provider model version, endpoint/region, decoding settings, context limit, and reasoning configuration where supported. Record unsupported differences.

Set matched ceilings for:

- Input/output tokens and model calls.
- Tool calls and concurrency.
- Wall-clock time.
- Estimated and actual spend.
- Network access, writable paths, and dependencies.
- Human approvals and interventions.

If defaults differ, publish separate **matched-budget** and **product-default** tracks. State whether warm-up, indexing, memory preparation, and skill-generation costs are included.

### C. Use frozen, representative tasks

Include bug fixes, multi-file features, refactoring with compatibility constraints, dependency changes, and unfamiliar-repository work. Supply identical initial repositories, prompts, and permitted documentation.

Keep hidden tests inaccessible to agents. Freeze scoring before runs. Use multiple paired repetitions per task and randomize execution order.

### D. Measure outcomes rather than native test volume

Primary outcome:

- Task success against independent hidden requirements and tests.

Secondary outcomes:

- Regressions and security violations.
- Time to accepted completion and timeout rate.
- Token use, model calls, tool calls, retries, and spend.
- Human interventions.
- Accuracy of completion claims.
- Recovery after injected failures.
- Patch maintainability under a blinded rubric.

Report per-task outcomes, aggregate rates, and uncertainty intervals. Do not count a system’s own unit tests as successful coding tasks.

### E. Test recovery and learning separately

For recovery, inject provider timeouts before/after dispatch, process termination, tool failure, authority revocation, browser closure, result tampering, and child-worker failure. Evaluate safe retry, durable evidence, uncertainty retention, and budget compliance.

For learning, compare memory/skill-enabled and disabled conditions using separate training and held-out tasks. Prevent cross-run contamination and include learning costs.

### F. Preserve an audit package

Retain exact prompts, source revisions, environment manifests, test receipts, model identifiers, budgets, tool traces, patches, hidden-test outcomes, and intervention logs. Redact secrets and sensitive content.

Only this kind of evidence can support claims such as “better at coding,” “faster,” or “cheaper.”
