## 2. Precedence: `ignore` is not deny-overrides

### Human triggers

The human gate evaluates branches in this order:

1. Resolve allowed identity and receiving scope.
2. **Listed sender + addressed trigger → explicit**, immediately.
3. Resolve the admission cell.
4. Consult the table only for addressed messages or messages in a listened, observed scope.
5. **Explicit table cell → explicit**, before follow-up handling.
6. **Eligible participating-thread follow-up → explicit for listed senders, inferred for others.**
7. **Inferred table cell → inferred** if evaluation is not `off`.
8. Otherwise reject with `not_a_member`, `admission_ignored`, or `no_mention`.

[Source: `upstream/superagent/src/policy.ts:190-210`]

Therefore:

- `ignore` does not override listed/addressed authorization.
- `ignore` does not override an eligible follow-up.
- Explicit table admission takes priority over follow-up inference.
- There is no universal deny-wins rule and no ask fallback.

The tests intentionally encode these precedence rules, but those assertions were not executed. [Sources: `upstream/superagent/src/policy.ts:196-209`; `upstream/superagent/tests/policy.spec.ts:103-115`, `143-158`]

### Follow-up semantics

Participation means any thread subscription or supplied ticket ID is not included in the thread’s context-only list. The helper does not inspect ticket completion state. The test fixture supplies an ended ticket and expects it to support inferred follow-up admission. [Sources: `upstream/superagent/src/policy.ts:128-131`; `upstream/superagent/tests/policy.spec.ts:29`, `67-75`]

Additional restrictions and exceptions:

- Context-only subscriptions do not confer follow-up authority.
- Listed follow-ups remain explicit even in evaluation mode `off`.
- Unlisted follow-ups require a mode other than `off`.
- Unlisted direct-message senders cannot obtain authorization **through the follow-up branch**.
- That direct-message restriction is not unconditional: an explicit admission cell is evaluated earlier and can authorize an unlisted direct message.

[Sources: `upstream/superagent/src/policy.ts:202-209`; `upstream/superagent/tests/policy.spec.ts:67-84`, `108-115`, `136-158`]

### Non-human triggers

Non-human triggers follow a separate path:

- A nonempty actor ID must be on the source’s bot list; otherwise rejection is `not_human`.
- The source must listen, and the trigger must address the agent or occur in an observed scope.
- Listed bots receive **inferred strength only**, even when addressed or associated with ticket threads.
- Listed-bot admission requires mode not `off`, but does not consult admission-table `ignore` cells.
- Senderless events use `unlistedUnaddressed`, including when an addressed marker is present. The cell must be `inferred`, and evaluation must not be `off`.

[Source: `upstream/superagent/src/policy.ts:170-187`]

## 3. Matching semantics

### Identities

`allowedSender()` selects the policy part keyed by `actor.source`, then searches with `sameName(entry.id, actor.id)`. `sameName()` performs lowercase equality. [Sources: `upstream/superagent/src/policy.ts:119-126`; `upstream/superagent/src/infra/text.ts:18-19`]

This establishes:

- source-local identity lists, not cross-source person mapping;
- case-insensitive equality, not glob, regex, substring, or prefix matching;
- use of that same comparison for all sources in these lookup functions, despite its GitHub-oriented comment;
- configured IDs trimmed by schema, but no incoming-ID trimming in the comparison helper;
- first-match behavior; allowed-list entries are not required to have unique IDs.

[Sources: `upstream/superagent/src/policy.ts:74`, `119-126`; `upstream/superagent/src/infra/text.ts:18-19`]

Bot-list parsing uses `z.array(AllowedSchema).catch([])`, so invalid bot-list parsing falls back to an empty list. [Source: `upstream/superagent/src/policy.ts:122-125`]

**Integration boundary:** identity lookup uses `trigger.actor.source`, while receiving-scope lookup uses `trigger.source`. The gate does not explicitly require those fields to agree. Correct trigger construction is an upstream responsibility; this is a static concern, not a demonstrated exploit. [Source: `upstream/superagent/src/policy.ts:172-174`, `193-195`]

### Admission rows and rules

- Admission lookup is exact source/row/cell property access.
- Missing rows or cells use `ADMISSION_DEFAULTS`.
- No wildcard-row matcher exists in `admissionOf()`.
- Only `unlistedAddressed` permits `explicit`; unaddressed cells allow `inferred` or `ignore`.
- Rule IDs allow 1–80 ASCII letters, digits, underscores, or hyphens.
- Duplicate configured rule IDs are rejected.
- Assessments must cover each enabled rule exactly once: no duplicate, unknown, disabled, or missing IDs.

[Sources: `upstream/superagent/src/policy.ts:13-16`, `40-46`, `74-82`, `134-140`]

## 4. Assessment acceptance

`assessmentOutcome()` provides another control after admission:

1. Validate exact enabled-rule coverage, even for non-accept decisions.
2. Build audit data.
3. Return non-accept decisions directly.
4. For acceptance, require direction establishing:
   - implementation requested;
   - target basis `specified` or `existing-standard`;
   - no required design decision;
   - valid nonempty bounded direction evidence.
5. Require a matched rule.
6. Require truthy `intent_evidence`.
7. Convert inferred acceptance outside `auto` into `ignore`/`observed`, with `would_accept`.
8. Otherwise return an accepted outcome carrying matched rule IDs.

[Source: `upstream/superagent/src/policy.ts:18-60`]

**Validation edge:** the function does not itself parse each judgment through `RuleAssessmentSchema` or trim `intent_evidence`. Whitespace-only intent evidence is not explicitly rejected by its truthiness check; stronger validation depends on callers. [Source: `upstream/superagent/src/policy.ts:14-16`, `40-53`]

`admitsInferred()` independently requires `auto`, a **nonempty** rule list, and every referenced rule currently enabled. [Source: `upstream/superagent/src/policy.ts:212`]

- a prohibition on blocking `gh`, `git`, or `lark-cli`;

## 6. Security boundaries and revalidation edges

### Human gate is not a standalone receiving-scope firewall

The human gate computes scope but does not begin with an unconditional `!scope.listened` rejection:

- listed/addressed authorization can return without listened scope;
- follow-up eligibility likewise lacks a listened-scope requirement;
- the machine gate explicitly requires listened scope;
- revalidation rejects an unlistened scope when both source and scope metadata are recorded.

[Source: `upstream/superagent/src/policy.ts:174-175`, `193-206`, `214-219`]

Tests separately intend source-scope handling to filter disabled, missing, or invalid sources. These scope assertions do not demonstrate equivalent rejection for every direct human-gate call. [Source: `upstream/superagent/tests/policy.spec.ts:31-52`]

### Mandate continuity

Revalidation:

- checks recorded receiving scope;
- preserves explicit follow-ups independently of continued allowed-list membership after that scope check;
- requires `auto` and enabled recorded rules for inferred follow-ups;
- requires continued bot-list membership for bot mandates;
- compares table strength using `ignore < inferred < explicit`;
- immediately validates a formerly unlisted addressed sender who is now listed;
- moves newly listed unaddressed senders to `listedUnaddressed`;
- rejects `listedUnaddressed` mandates if their sender is no longer listed;
- requires `auto` and enabled rules for observation-tagged admission/listed/bot mandates.

[Source: `upstream/superagent/src/policy.ts:140`, `213-243`]

Important edges:

- `rulesOn()` treats absent or empty rule arrays as valid, unlike `admitsInferred()`.
- Missing source/scope metadata skips receiving-scope checking.
- Missing observation metadata can skip the final observation-specific check for non-follow-up bases.
- Revalidation checks listened scope, not continued observation. The parameterized test oracle intends some mandates to survive `all` → `mentions`.

[Sources: `upstream/superagent/src/policy.ts:217-242`; `upstream/superagent/tests/policy.spec.ts:175-202`]

### Version and pause

Policy versioning includes revision, rules, evaluation mode, and per-source policy parts. It excludes pause, executor settings, evaluation timeout/models, and source-instance configuration. Version equality therefore does not prove unchanged receiving scope. `policyEffects()` separately reports rule changes, requester authorization loss, and cessation of inferred acceptance. [Sources: `upstream/superagent/src/policy.ts:111-118`, `142-164`; `upstream/superagent/tests/policy.spec.ts:224-230`]

The returned policy exposes `paused`, but neither `gate()` nor `revalidate()` rejects on pause by itself. Pause enforcement must occur elsewhere. [Source: `upstream/superagent/src/policy.ts:189-243`]

## 9. Synthesis-ready conclusion

The central distinction is between **authority to originate work**, **assessment eligibility**, and **execution containment**. This policy implements the first two, not a comprehensive execution sandbox.

Most consequential findings:

1. **`ignore` is not deny-overrides:** listed/addressed messages and eligible follow-ups take precedence.
2. **Default inferred work is observational:** automatic acceptance requires `auto` and matched enabled rules.
3. **Identity matching is source-local, case-insensitive equality**, while actor/trigger source consistency is an integration responsibility.
4. **The human gate is not a standalone receiving-scope firewall.**
5. **Revalidation depends on recorded basis metadata**, with deliberate exceptions including persistent explicit follow-up authority.
6. **Command blocking is explicitly a PATH guardrail, not an OS security boundary.**
7. **Runtime behavior remains unverified:** the required single attempt failed before any policy tests ran.
