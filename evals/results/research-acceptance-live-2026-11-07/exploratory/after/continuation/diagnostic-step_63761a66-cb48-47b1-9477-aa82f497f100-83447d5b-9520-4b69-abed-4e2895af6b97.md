### Human-trigger precedence

The gate evaluates human triggers in this order:

1. **Allowed sender plus addressed trigger → explicit**, bypassing the admission table.
2. Otherwise determine the admission cell from listed/addressed status.
3. Admission-table reception requires an addressed trigger, or a listened-and-observed scope.
4. **Explicit admission cell → explicit**, before follow-up handling.
5. A participating ticket thread admits a follow-up: explicit for allowed senders, inferred for others. Unallowed direct-message senders cannot use this shortcut; inferred follow-ups require mode other than `off`.
6. Otherwise an inferred admission cell works only outside `off`.
7. Otherwise reject.

Evidence: `upstream/superagent/src/policy.ts:191–211`.

Consequences:

- **`ignore` is not a universal deny:** a participating-thread follow-up can bypass an ignored cell.
- An unlisted sender’s addressed message can be explicitly authorized by its row, including in `off`.
- Context-only subscriptions do not establish participation. The participation helper itself does not filter supplied tickets by ended status. (`upstream/superagent/src/policy.ts:130–140,197–210`)

### Nonhuman triggers

- A nonempty actor ID must appear on the source’s bot list.
- Scope must be listened to and either addressed or observed.
- Listed bots remain inferred, even when addressing the agent or entering an existing ticket thread.
- Senderless events use `unlistedUnaddressed`, which must grant inferred admission.
- Both paths reject when evaluation is `off`; neither uses human follow-up shortcuts.

## Rules, matching, and acceptance

### Default rules

Two enabled natural-language rules ship by default:

- **Copy:** explicit corrections to typos, wording, punctuation, or existing translations while preserving product promises and business meaning.
- **Visual:** explicit local implementation fixes with a specified target or established existing standard; no invented styling, redesign, behavior, or adjacent undefined restyling. Unsettled direction should remain observation-only.

These are instruction prose, not deterministic semantic matchers. (`upstream/superagent/src/policy.ts:62–64`)

### Assessment checks and precedence

`assessmentOutcome` enforces:

1. Exactly one judgment for every enabled rule; duplicate, disabled, unknown, or missing IDs are rejected.
2. All judgments marked matched contribute; there is **no first-match winner or deny-rule hierarchy**.
3. Non-accept decisions return with audit data before acceptance-specific checks.
4. Acceptance requires direction that is structurally valid, implementation-requested, based on a specified/existing-standard target, and free of open design decisions.
5. Unsettled direction returns `directionUnsettled`; no matches returns `noRuleMatched`.
6. Acceptance requires truthy `intent_evidence`.
7. Inferred acceptance outside `auto` becomes `ignore`, preserving `would_accept: true` and a proposal.
8. Successful acceptance records all matched rule IDs.

Evidence: `upstream/superagent/src/policy.ts:13–59`.

`admitsInferred` separately requires `auto`, a nonempty rule list, and every referenced rule currently enabled. (`upstream/superagent/src/policy.ts:212`)

**Limitation:** these checks do not establish evidence authenticity or correct natural-language interpretation. The function checks judgment coverage but does not itself parse each judgment through `RuleAssessmentSchema`. This is a source-level boundary, not a demonstrated exploit. (`upstream/superagent/src/policy.ts:13–59`)
