## Authorization → ingestion → scheduling → execution → delivery

### 1. Authorization is application policy, not simply “mention means execute”

The application separates source scope, sender authorization, admission strength, and mandate revalidation:

- Non-human traffic is handled separately: listed bots may enter as inferred candidates, senderless system/CI events have a distinct path, and other bots are rejected.
- An allowed human sender explicitly addressing the agent receives explicit strength.
- Admission rules and followed-thread context can admit other messages; inferred acceptance depends on evaluation mode.
- Existing mandates are revalidated using their recorded basis.

**Source:** `upstream/superagent/src/policy.ts:167–236`.

Existing tests cover source-specific authorization lists, disabled/unloaded sources, direct-message restrictions, automated traffic, admission-table behavior, and evaluation-off behavior (`upstream/superagent/tests/policy.spec.ts:32–130`). That suite passed.

**Important qualification:** “Only allowlisted people can ever affect a ticket” is too strong. Follow-ups, inference, configured bots, and admission rules are intentional additional paths.

### 2. Ingestion is durable-first and deduplicated at the core boundary

The existing intake test submits the same trigger twice and expects `stored` then `duplicate`. A source-filtered trigger gets a recorded filtering disposition. A trigger spanning multiple threads records correlation but queues evaluation on its primary thread.

**Evidence:** `upstream/superagent/tests/core-engine.spec.ts:74–94`.

The engine test harness also exposes a distinct assessor request queue and executor launch/delivery interfaces, rather than directly executing every received event (`upstream/superagent/tests/core-engine.spec.ts:15–72`).

**Boundary:** This verifies engine intake under tests. It does not establish lossless real-world GitHub polling/webhook or Feishu ingestion under outages.

### 3. Work scheduling has explicit lifecycle and capacity accounting

The executor maintains a persistent worker-session identity per ticket: `worker-<ticketId>` (`upstream/superagent/src/executor/dsh.ts:1–26`).

`WorkerSlots` counts running workers and startup reservations. Reservations are synchronous before asynchronous startup, preventing two starts from consuming the same last slot. A human follow-up may use **one extra slot** beyond the configured limit.

**Source:** `upstream/superagent/src/executor/dsh.ts:160–200`.

Capacity includes shell jobs and subagents that remain active after a worker turn ends—not merely whether the model is currently generating. Existing runtime-concurrency tests exercise this behavior, stop/hand-off cleanup, and restart delivery cases (`upstream/superagent/tests/runtime-concurrency.spec.ts:264–305, 330–395, 505–544`). All 56 tests in that suite passed.

### 4. Isolation means per-ticket session/workspace—not proven security containment

The executor explicitly describes one persistent worker session and workspace directory per ticket. It uses host-provided sessions, agents, subprocesses, and background-job services. Worktree names incorporate a validated name and stable ticket-ID suffix.

**Source:** `upstream/superagent/src/executor/dsh.ts:1–82`.

This supports **organizational and execution-context separation**. It does **not**, by itself, prove container, VM, kernel, network, or credential isolation. The targeted tests use an in-memory host fixture, not hostile-code sandbox escape tests.

### 5. Input and result delivery include retry/deduplication mechanisms, but external exactly-once delivery is unproven

The engine fixture explicitly models stable-ID outbox deduplication and distinct delivery/read acknowledgements (`upstream/superagent/tests/core-engine.spec.ts:35–72`).

The delivery tests include failed durability-barrier retry, history-read retry/pagination, consumption during initial history loading, cancellation during loading, and recognizing messages held in inbox/history (`upstream/superagent/tests/delivery.spec.ts:89–137`).

Outbox tests verify:

- messages remain held while processing is paused and send after resume;
- a missing source plugin leaves a message waiting until its source kind registers.

**Evidence:** `upstream/superagent/tests/outbox.spec.ts:17–30`.

All relevant suites passed. A complete line-by-line audit of external channel send/acknowledgement crash windows was **not completed**; do not infer universal exactly-once delivery.

## Recovery and negative cases

Concrete implementation choices include:

- **Transient failures:** three retry attempts with an initial **15-second** backoff; recognition includes network errors, rate limits, HTTP 408/429, and server errors.
- **Prepare failure:** deliberately not automatically retried because a leftover directory could otherwise be mistaken for a prepared workspace.
- **Prepare timeout:** **10 minutes**.
- **Background-work limit:** **30 minutes** after the worker turn ends.
- **Shutdown background-stop allowance:** **10 seconds**.

**Source:** `upstream/superagent/src/executor/dsh.ts:27–56`.

These are useful defensive lifecycle mechanisms. However, transient-error classification partly relies on matching error text, and prepare-command recovery intentionally requires care with partial workspace state.
