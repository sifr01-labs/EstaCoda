## Security findings, prioritized

### Critical / High: no confirmed vulnerability established

The inspected code preserves several important authority boundaries:

1. **Child exposure is bounded by parent visibility and explicit restrictions.**
   Candidate tools are matched against parent-visible names, and parent metadata is used when available. Requested names/toolsets narrow access; blocked names/prefixes, excluded toolsets, risk restrictions, and delegation depth restrictions still apply.
   Evidence: `src/delegation/toolset-security.ts:100–161`, `src/delegation/toolset-security.ts:171–228`.

2. **Task approval cannot override an explicit base-policy denial or a Task/Step forbidden risk class.**
   The denial check precedes approval matching; Task and Step ceilings are checked before an approved fingerprint can authorize the operation.
   Evidence: `src/tasks/task-approval-service.ts:264–295`.

3. **Approved execution is revalidated at dispatch, not merely assessment.**
   Dispatch checks the inherited authorization, current Task/Step/Attempt records, terminal status, active plan revision, attempt fencing token, approval identity, hardline command floor, and current narrowed decision. Matching approval is then consumed.
   Evidence: `src/tasks/task-approval-service.ts:110–128`, `src/tasks/task-approval-service.ts:249–261`.

These are positive implementation findings, not proof of complete runtime enforcement.

### Medium: broader default exposure makes runtime enforcement release-critical

Defaults allow `workspace-write`, impose no default toolset allowlist, and retain parent-visible execution/editing tools unless another restriction removes them. This is deliberate behavior, not a demonstrated bypass.

- Defaults and exclusions: `src/config/delegation-defaults.ts:17–33`.
- Explicit test expectation includes `terminal.run` and `file.write`: `src/delegation/toolset-security.test.ts:16–31`.
- Task executor supplies the approval-wrapped runtime policy: `src/tasks/agent-step-executor.ts:194–209`.
- Task/Step tool filtering additionally checks forbidden risks, blocked tools, tool allowlists, toolsets, and child-task authority: `src/tasks/agent-step-executor.ts:587–608`.

**Release implication:** these focused tests do not demonstrate end-to-end that every exposed execution/editing operation reaches dispatch authorization before its side effect. Treat that as an integration-verification gap, not an established exploit.

### Low: multi-toolset reporting can conflict with downstream subset checks

The resolvers accept a tool when **any** toolset matches, but report **all** toolsets attached to accepted tools. The delegated-child validator rejects effective toolsets outside persisted/Step toolset sets.

- Acceptance and result construction: `src/delegation/toolset-security.ts:65–67`, `src/delegation/toolset-security.ts:85–87`, `src/delegation/toolset-security.ts:212–216`.
- Downstream subset validation: `src/tasks/agent-step-executor.ts:559–572`.

This creates a possible **fail-closed availability issue** for multi-tag tools unless persisted authority includes all reported tags. No failing end-to-end case was demonstrated; the focused tests do not exercise this validator/resolver combination.
